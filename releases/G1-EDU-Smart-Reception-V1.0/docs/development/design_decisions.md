# 关键设计决策

每条按“工程问题 → 方案 → 机制 → 收益 → 限制”记录。

## 1. 为什么所有回复必须经过一个 Worker

- **问题**：ROS 回调可能在任意时刻触发；若直接在回调里调 HTTP、发 TTS，连续提问会导致回复乱序、动作与回答错配。
- **方案**：回调只做“归一化 → 过滤 → 去重 → 入队”，业务全部交给唯一 worker 线程。
- **机制**：有界 FIFO（等待上限 3）+ 单线程串行 + 统一 `publish_reply()`。
- **收益**：回复顺序严格等于请求顺序；动作执行期间后续请求自动排队。
- **限制**：吞吐上限由单 worker 决定；Ollama 慢时队列会满（返回忙碌提示，不丢已接受请求）。

## 2. 为什么有界队列 + 拒绝最新请求

- **问题**：无界队列在高频误识别下会无限堆积，最终内存与延迟失控。
- **方案**：容量满时拒绝**新**请求，保留已接受请求；忙碌提示进入独立有界通知队列（容量 2），且只在所有已接受请求处理完后发布。
- **收益**：系统在持续高压下仍然有界，且不会“提示插队”。
- **限制**：极端情况下用户会被拒绝，需要重说一次。

## 3. 为什么状态要独立 Provider，而不是 Router 直接订阅 `/lowstate`

- **问题**：`/lowstate` 约 1kHz、结构复杂（35 路电机、IMU），直接放进语音进程会让业务代码被高频回调淹没。
- **方案**：Provider 单独订阅、降频到 2Hz、输出结构稳定的聚合 JSON，并携带每个字段的有效性。
- **收益**：语音侧只处理“状态是否可用”，不感知原始消息结构；Provider 可独立重启。
- **限制**：多一跳缓存，最坏引入约 0.5–5s 的时效延迟（由 5s 缓存超时兜底）。

## 4. 为什么必须有 FactRiskGuard

- **问题**：模型会编造价格、人数、成果、设备型号、实时状态（真实发生过报价错误）。
- **方案**：在进入 Ollama 队列**之前**做程序化拦截：
  - PRICE → 直接安全兜底，不调用模型；
  - REALTIME_STATUS → 直接兜底；
  - LAB_FACT → 先查本地知识库，可靠命中才用，否则兜底；
  - NORMAL → 放行。
- **收益**：高风险问题不依赖提示词自觉。
- **限制**：规则是白名单式的，语义边界需要持续测试（已用 119 项测试锁定，含 8 项防过度拦截用例）。

## 5. 为什么动作要程序级白名单

- **问题**：人形机器人错误动作有物理风险；模型输出不可控。
- **方案**：`ActionCommandMapper` 输出固定的 6 个动作名，出口二次校验 ID；`hand_on_heart/33` 永久禁用。
- **机制**：判定顺序 禁用 → 否定 → 疑问 → 最长短语匹配；含糊命令不猜，改为能力澄清。
- **收益**：任何输入都不会生成白名单外动作；否定句（“不要挥手”）不会触发动作。
- **限制**：覆盖的是有限表达；新说法需要按证据扩充并加测试。

## 6. 为什么动作结果要串行等待且不重试

- **问题**：执行器结果协议**没有请求 ID**，并发时无法可靠归属；物理动作重复执行有风险。
- **方案**：同一时刻只允许一个动作在途；按“动作名 + 发送前序号快照”匹配；45s 超时（大于执行器最坏 38s）。
- **收益**：单请求场景下关联可靠；不确定时不重复动作。
- **限制**：不支持并发动作；同名动作连续执行存在理论上的延迟结果误配风险。

## 7. 为什么 ASR 归一化只做有限词典

- **问题**：ASR 会把“脑机接口”识别成“脑急接口/脑筋接口/手机接口”等。
- **方案**：只对**有真实日志证据且明显非词**的变体做替换；含“不要/别/停止/取消”时整体跳过；不碰数字；保留原文。
- **收益**：修正常见错识，同时不会把“手机接口是什么”这种合法提问改坏。
- **限制**：覆盖不封闭，新变体需要按证据补充。

## 8. 为什么 TTS 分句 + 估算等待

- **问题**：长文本一次性下发会被截断；句间无间隔听感差。
- **方案**：中文分句、逐句 `TtsMaker`、按字数估算播放时长并插入 `pause_ms`（1500ms）。
- **收益**：长回答完整播出，节奏可控。
- **限制**：`TtsMaker ret=0` 只代表调用成功，**没有真实播放完成事件**；等待时间是估算值。
