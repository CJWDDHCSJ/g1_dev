# P0-19 连续对话与 InteractionManager（阶段摘要）

- **时间**：2026-11-02
- **完整报告**：[P019_INTERACTION_MANAGER_REPORT.md](P019_INTERACTION_MANAGER_REPORT.md)
- **结论**：把“回调里直接干活”改成“回调只入队、单 worker 串行处理”，解决了连问时回复乱序、重复回答、停机卡死三个问题。

## 一、问题

P0-16 的 Router 直接在 `/g1/asr_text` 回调里跑意图、HTTP、发布。后果：

1. 连续两次提问时，若第一句模型慢、第二句本地快，**回复顺序与提问顺序不一致**；
2. 同一句被 ASR 重复输出时，会被回答两遍；
3. 停机时若正卡在 HTTP，进程要等超时（最长 60 s），超过 systemd 的 15 s 停止期限会被强杀。

## 二、方案

| 机制 | 参数 | 作用 |
|---|---|---|
| 文本过滤 | 语气词 ≤4 字、纯标点、空文本 | 去掉“嗯”“啊”类噪声，保留“你好/IMU/G1/停止” |
| 去重 | 1200 ms 窗口 | 同一句话只处理一次 |
| 有界 FIFO | `max_pending = 3`（不含处理中） | 队列满时拒绝**最新**请求并说明原因 |
| 单 worker | 1 个线程 | 串行处理，保证顺序 |
| 状态机 | 13 个状态、白名单转移 | 请求生命周期可观测、非法转移被拒 |
| 忙碌提示 | 独立队列容量 2，`pending_count()==0` 时才发 | 提示不插队 |
| 优雅停机 | SIGINT → 置标志 → 中断 HTTP → 唤醒等待 → join | 停机不超时 |

## 三、验证

| 项目 | 结果 |
|---|---|
| 单元测试 | 76 项（过滤/去重/队列/状态机/停机/统计） |
| 停机耗时 | 空闲 0.29 s；HTTP 中 0.79 s；动作等待 0.29 s |
| 顺序 | 连发多条，`/g1/tts` 顺序与请求顺序一致 |
| 队列满 | 第 N+1 条返回 `REJECTED (QUEUE_FULL)`，忙碌提示最后播报 |

## 四、遗留

- 吞吐上限 = 单请求耗时（模型 5.5–7.0 s 期间其他问题排队）；
- 忙碌提示只有一句固定话术，不区分“排队中”与“已丢弃”；
- 请求记录不持久化，进程重启后统计归零（有意为之，避免长期增长）。
