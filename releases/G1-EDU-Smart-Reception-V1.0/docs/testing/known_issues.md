# 已知问题与限制

> 逐条给出：现象 → 影响 → 当前缓解 → 根治方向。所有条目均为 V1.0 冻结时的真实状态。

## 1. ASR 专有名词误识（未封闭）

- **现象**：`脑机接口` 被识别为 `脑急接口` / `脑筋接口` / `手机接口`。
- **影响**：前两种已由 `ASR001` 纠正；第三种会答偏，用户需重说。
- **缓解**：有限词典 + 控制词保护；不做模糊匹配（会污染合法提问）。
- **根治**：按真实日志证据持续扩充词表；或引入领域语言模型重打分（V1.0 之后）。

## 2. 归一化覆盖有限

- **现象**：只覆盖有日志证据的别名（`ASR001`、`ASR002`）。
- **影响**：新变体仍会漏。
- **缓解**：日志记录 `raw_len + raw_digest + normalized`，便于事后取证。
- **根治**：同上；禁止未经证据的“猜词”。

## 3. ASR001 缺少真机验证

- **现象**：专项真机输入输出为“手机接口”，未触发该分支。
- **影响**：该规则目前只有单元测试证据（22 项中的若干条）。
- **缓解**：文档与报告中明确标注“未真机验证”，不写成通过。
- **根治**：出现真实“脑急接口/脑筋接口”输入时补记录。

## 4. Action Result 无请求 ID

- **现象**：结果消息只有 `success:<name>:<id>`，不携带请求标识。
- **影响**：同名动作连续执行时，理论上可能把延迟结果误配给新请求。
- **缓解**：单 worker 串行 + 动作名匹配 + 发送前序号快照 + 45 s 超时 + 不重试。
- **根治**：结果协议增加请求 ID（需要改执行器与 Router 双方）。

## 5. 结果前缀不完全对齐

- **现象**：执行器会发 `completion_unknown:...` 与 `completed_with_rpc_error:...`，Router 只识别 `success/failed/timeout/rejected`。
- **影响**：这两类情况必然退化为 45 s 超时，用户听到“未收到结果”。
- **缓解**：超时话术明确“不会自动重复执行”，避免误导。
- **根治**：统一终态前缀，或在协议层加请求 ID 与状态枚举。

## 6. IMU 只回答接收与时效

- **现象**：`imu.data_available` 只表示“字段长度合法且持续到达”。
- **影响**：不能回答“传感器是否健康”“姿态是否准确”。
- **缓解**：话术明确“还没有完成完整的传感器健康诊断”。
- **根治**：接入标定与自检数据（当前没有可靠来源）。

## 7. `TtsMaker ret=0` ≠ 播放完成

- **现象**：API 只返回调用结果，没有播放完成事件。
- **影响**：句间节奏靠估算（250 ms/字符 + 1500 ms 间隔），长句可能偏短。
- **缓解**：长回答分句播报；`SPEAKING` 状态保留但**不伪造**进入。
- **根治**：需要底层提供播放完成回调。

## 8. 配置文件中的 `volume` 未生效

- **现象**：`tts_config.json` 有 `volume: 80`，节点只读取未应用（启动日志明确警告）。
- **影响**：改配置不会改变音量，需在设备侧设置。
- **缓解**：日志警告 + 本文档标注。
- **根治**：接入 `AudioClient` 的音量接口（若底层支持）。

## 9. 动作真机覆盖不足

- **现象**：仅 `wave`（26）有真机验收；`wave_low/hands_up/clap/heart/victory` 只有白名单与 Mock。
- **影响**：不能宣称“六个动作都已验证”。
- **缓解**：README 与白名单表逐项标注验收状态。
- **根治**：逐项真机验收（需现场安全确认）。

## 10. 动作失败后执行器保持锁定

- **现象**：RPC 未确认 / 稳定期状态突变 / 完成超时时，`action_busy_` 不释放。
- **影响**：后续动作请求一律 `rejected`，必须人工确认后恢复。
- **缓解**：这是有意的安全设计；日志明确提示 “Executor remains locked”。
- **根治**：引入带外部确认的复位流程（当前不自动化）。

## 11. 核心交互不依赖深度相机

- **现象**：无视觉识别、人脸识别、自主导航、语义地图。
- **影响**：不能做“看着人说”“带路”“识别设备”等演示。
- **缓解**：所有宣传与文档只描述语音 + 状态 + 白名单动作。
- **根治**：视觉能力恢复后的独立升级方向。

## 12. 大模型不在机器人本地

- **现象**：Ollama 运行在外部主机，通过 HTTP 调用。
- **影响**：断网时通用问答不可用（退化为“无法连接对话模型”）。
- **缓解**：本地知识库、状态、动作、问候、兜底全部可用。
- **根治**：Jetson 本地小模型部署（受内存与算力限制，属 V1.0 之后）。

## 13. 状态字段覆盖有限

- **现象**：关节温度单位未确认、索引与关节名映射未知；里程计未纳入。
- **影响**：不能播报“哪个关节多少度”，也不能回答位置/里程问题。
- **缓解**：`temperature_max_raw` 只做内部诊断；`unit_confirmed=false` 显式标记。
- **根治**：与固件方确认单位与索引映射。

## 14. 业务单点与重启窗口

- **现象**：Router 崩溃会中断全部业务。
- **影响**：systemd 3 s 后拉起，期间约 1–2 s 无响应。
- **缓解**：`Restart=always`、`StartLimitBurst=5`；数据面（状态、动作）已独立进程。
- **根治**：多实例 + 请求路由（当前场景不需要，且会引入双 Router 风险）。

## 15. 未做长时间压力测试

- **现象**：>1 小时连续接待的稳定性、内存增长、日志增速无专项数据。
- **影响**：不能给出“可连续运行 N 小时”的承诺。
- **缓解**：日志轮转 + 磁盘监测 + 队列有界，降低长跑风险。
- **根治**：安排一次真实长跑并采集 CPU/内存/磁盘曲线。
