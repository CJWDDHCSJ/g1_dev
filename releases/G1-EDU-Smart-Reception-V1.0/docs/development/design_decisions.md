# 关键设计决策记录

> 采用“背景 → 决策 → 备选方案 → 后果”的记录方式。每条决策都能在源码中找到落地位置。

## D1 业务集中在单个 Router 进程

- **背景**：意图、风控、知识库、动作映射需要共享同一份配置与上下文；跨进程同步会引入额外故障点。
- **决策**：一个 `g1_voice_router` 进程内组合全部业务模块，模块之间用 C++ 对象调用而非话题。
- **备选**：拆成 intent 服务 / guard 服务 / kb 服务，用 ROS 服务调用。
- **后果**：优点是无序列化开销、调试直观、单测容易；缺点是 Router 崩溃即全业务中断。缓解手段是 `Restart=always` + 3 s 重启，并且**数据面（状态、动作）已拆到独立进程**，重启 Router 不影响物理接口。

## D2 状态感知独立成 Provider

- **背景**：`/lowstate` 实测约 1050 Hz，35 路电机；若在业务进程内消费，1 kHz 回调会与 HTTP、动作等待争抢执行上下文。
- **决策**：Provider 独立进程，高频回调只更新缓存，2 Hz 聚合发布。
- **备选**：Router 直接订阅四路原生话题。
- **后果**：多一跳话题与 0–500 ms 延迟，但换来降频、四态判定集中、可独立重启；也让 `robot_state_evaluator` 成为可单测的纯逻辑（44 项）。

## D3 唯一 worker 串行处理请求

- **背景**：ROS 回调随时触发，并发处理会导致回复乱序、动作与回答错配。
- **决策**：回调只入队，唯一 worker 串行执行；所有回复走 `publish_reply()` 单一出口。
- **备选**：线程池 + 请求 ID 排序；或在回调里直接处理。
- **后果**：吞吐上限 = 单请求耗时（模型问答约 5.5–7.0 s 期间其他请求排队），队列只有 3 个等待位，满了明确拒绝。这个代价被接受，因为接待场景的并发度是“偶尔连问两句”，不是高并发服务。

## D4 队列满时拒绝最新请求，忙碌提示不插队

- **背景**：用户快速连问时，若静默丢弃或让提示抢先播报，会出现“提示排在答案前面”的错乱。
- **决策**：拒绝**最新**请求并返回 `QUEUE_FULL`；忙碌提示进入容量 2 的独立队列，只在 `pending_count()==0` 时由 worker 发布。
- **后果**：用户会听到明确的“问题有点多，请稍等再问”，而不是莫名无响应；提示永远不会切断正在生成的回答。

## D5 事实风控放在程序里，而不是提示词里

- **背景**：提示词只能“劝阻”模型，无法“保证”它不编造价格与实时状态。
- **决策**：`FactRiskGuard` 在文本进入模型之前做四分类，价格与实时状态直接短路。
- **备选**：只靠 system prompt；或用另一个模型做审核（多一次推理、不可解释）。
- **后果**：规则式判定会有误拦（已用 8 项用例校准），但换来确定性：价格类问题 0 次模型调用，日志可审计每个拦截原因。

## D6 知识问法与状态问法用“形式”区分

- **背景**：“IMU 是什么”与“你的 IMU 正常吗”共享关键词，却应走完全不同的路径。
- **决策**：先看问法形式（是什么/如何/原理 → 知识），再看实体词与语境词；并对“什么状态”单独豁免。
- **后果**：规则变多、顺序敏感，因此用 96 项意图测试 + 119 项风控测试锁住边界；新增问法必须同时补测试。

## D7 状态数值只在 VALID 时出现，其余输出 null

- **背景**：用 `0` 表示缺失会让上层误判成“电量 0%”。
- **决策**：`to_json` 中非 `VALID` 的数值一律 `null`；话术层同样只在 `VALID` 时说数字。
- **后果**：JSON 消费方必须处理 `null`，但“没有数据”与“数据是 0”彻底分开。

## D8 SOC 只取 BMS 字段，并用跳变检测兜底

- **背景**：电压反推 SOC 精度差；BMS 偶发异常帧也会造成明显跳变。
- **决策**：只用 `/lf/bmsstate` 的 `soc`；范围 0–100；60 s 内跳变 ≥15 个百分点判 `INVALID`。
- **依据**：P0-18 的 60 秒 1229 样本窗口内零跳变，跨小时单调下降与电压交叉验证一致。
- **后果**：阈值是经验值，极端工况（如低温大电流）可能误判为 `INVALID`，此时系统只会说“无法确认”，不会说错数字。

## D9 动作白名单 + 出口二次校验

- **背景**：动作 ID 与固件强绑定，模型输出不可控，ID 33 在真机上有异常表现。
- **决策**：短语表 → 白名单 ID → 出口校验（0 或 33 一律拒绝）；否定/疑问不进入匹配。
- **后果**：未收录说法退化为“能力提示”而不是猜测；用户可能要多说一遍，但不会误触发动作。

## D10 动作失败不重试，且执行器保持锁定

- **背景**：物理动作的“不确定状态”比“失败”更危险——机器人可能正处在动作中间。
- **决策**：RPC 未确认、稳定期状态突变、完成超时三种情况都不释放 busy，要求人工确认。
- **后果**：可能出现“必须先人工恢复才能继续演示”的中断，这是有意选择的安全优先。

## D11 动作结果按“名字 + 序号快照”匹配

- **背景**：Unitree 动作结果协议没有请求 ID。
- **决策**：Router 记录发送前的 `action_result_seq_`，只接受序号变化后、动作名匹配的结果；配合单 worker 串行与 45 s 超时。
- **后果**：同名动作连续执行时理论上可能误配延迟结果；`completion_unknown` 类结果只能退化为超时。根治需改协议（路线图项）。

## D12 TTS 用估算节奏而不是等待播放完成

- **背景**：`TtsMaker` 只返回调用结果，没有播放完成事件。
- **决策**：按 UTF-8 字符数估算（250 ms/字符，最少 1 s），句间再等 1500 ms；所有等待可被停机打断。
- **后果**：语速差异会导致句间偶尔偏长或偏短；换来的是“不阻塞、可中断、不需要底层改造”。系统在文档与日志中都明确标注 `ret=0 ≠ 播放完成`。

## D13 大模型放在机器人外

- **背景**：Orin NX 同时跑 4B 模型会与语音、状态、动作链路抢资源。
- **决策**：Ollama 部署在外部主机，HTTP `POST /api/chat`，`stream=false`，超时 60 s。
- **后果**：依赖局域网；断网时退化为本地能力（问候/知识库/状态/动作/兜底）。之所以不用流式，是因为当前 TTS 按整段分句播报，流式收益有限而复杂度显著上升。

## D14 user 级 systemd + Linger

- **背景**：机器人上不方便长期开 root 会话；演示要求“开机就能用”。
- **决策**：全部服务以 `unitree` 用户运行，`g1-voice-stack.target` 聚合，`loginctl enable-linger` 保证无人登录也启动。
- **后果**：unit 内路径硬编码（改动需同步脚本），但获得了崩溃自愈、统一日志、优雅停机的完整能力。
